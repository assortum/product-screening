# Product Screening — база первичной проверки товаров для Ozon

Статическая поисковая база для предварительного отбора товаров перед закупкой и запуском на Ozon в России.

Главная задача проекта — по связке **«Основная категория Ozon → Категория → Тип товара»** быстро понять регуляторную сложность входа:

- нужен ли **Честный знак сейчас**;
- есть ли **утверждённый будущий этап** обязательной маркировки;
- участвует ли товар только в **эксперименте / пилоте**;
- какие **ТН ВЭД ЕАЭС** реалистичны;
- какие характеристики меняют классификацию;
- требуются ли **декларация, сертификат, СГР, регистрация или иной специальный документ**;
- возможен ли сценарий с **отказным письмом**;
- насколько товар удобен для дальнейшего отбора с точки зрения регуляторной нагрузки.

Это **screening-база**, а не автоматическое юридическое заключение и не классификационное решение таможенного органа.

## Что означает цвет

Цвет — это **регуляторная сложность входа**, а не решение «продавать / не продавать».

### GREEN — ПРОСТОЙ ВХОД

Типовой сценарий не показывает существенной обязательной регуляторной нагрузки.

Обычно:

- Честный знак не выявлен;
- обязательная декларация / сертификация / СГР не выявлены для зафиксированного сценария;
- отказное письмо вероятно возможно после подтверждения окончательного кода и назначения.

GREEN нельзя назначать только потому, что товар выглядит простым.

### YELLOW — ВНИМАНИЕ

Есть существенная развилка.

Примеры:

- материал меняет ТН ВЭД и документы;
- детское / взрослое назначение даёт разные режимы;
- бытовое / профессиональное / медицинское назначение меняет требования;
- один вариант GREEN, другой RED;
- товар может попадать в эксперимент;
- точного описания Ozon недостаточно для 10-значного ТН ВЭД;
- требуется дополнительная идентификация состава, напряжения, мощности, конструкции, назначения и т. п.

### RED — СЛОЖНЫЙ ВХОД

Во всех основных реалистичных сценариях есть существенная обязательная нагрузка.

Например:

- обязательная маркировка;
- обязательный сертификат / декларация / СГР;
- специальная государственная регистрация;
- ГИИС ДМДК / УИН для ювелирных изделий;
- медицинский режим;
- иные обязательные требования, делающие вход сложным.

### PENDING — НЕ ПРОВЕРЕНО

Тип товара ещё не прошёл нормативный screening.

## Главные правила нормативного анализа

### 1. Не смешивать три состояния Честного знака

В карточке всегда отдельно хранятся:

- `current` — обязательная маркировка действует сейчас;
- `future` — есть уже утверждённый нормативным актом будущий обязательный этап;
- `experiment` — эксперимент / пилот.

**Эксперимент не является будущей обязательной маркировкой.**

Проект постановления, новость, обсуждение, дорожная карта или предложение также не считаются `future = yes`, пока нет утверждённого нормативного основания.

### 2. Совпадения одного ТН ВЭД часто недостаточно

Для Честного знака область применения может определяться сочетанием:

`ТН ВЭД + ОКПД2 + наименование / назначение товара`.

Поэтому совпадение только по группе ТН ВЭД может означать лишь необходимость дополнительной проверки.

### 3. Не выдумывать точный 10-значный код

Если из названия Ozon невозможно доказать полный код, нужно давать:

- несколько реалистичных кодов;
- 4-/6-значную группу;
- или более широкую классификацию.

В `influences` перечисляются характеристики, без которых нельзя выбрать окончательный вариант.

Пример: материал, состав, назначение, возраст пользователя, питание от сети, напряжение, мощность, наличие двигателя, способ применения, конструкция, размеры.

### 4. Отказное письмо не назначается автоматически

Отказное письмо — не «универсальный документ для простого товара».

Его можно указывать как вероятный сценарий только если после точной классификации товар не попадает в обязательную оценку соответствия.

Если по ТР ТС / ТР ЕАЭС нужен сертификат, декларация, СГР или специальная регистрация, отказное письмо их не заменяет.

### 5. Специальные режимы важнее отсутствия ЧЗ

Отсутствие Честного знака не означает простой вход.

Пример: ювелирное изделие может не иметь ЧЗ ГИС МТ, но иметь обязательные требования ГИИС ДМДК, УИН и пробирного надзора.

### 6. Детское назначение проверяется отдельно

Товар, который в обычном взрослом сценарии прост, при назначении для детей может попадать под ТР ТС 007/2011, ТР ТС 008/2011 или другую специальную область регулирования.

### 7. Данные должны быть актуальны на дату анализа

Перед добавлением нового пакета необходимо заново проверять актуальность норм на текущую дату. Нельзя полагаться только на ранее найденную статью, если правило могло измениться.

## Важная действующая точечная поправка

Постановление Правительства РФ №1458 об эксперименте по отдельным товарам для дома и интерьера включает, среди прочего, отдельные товарные группы/коды, связанные с:

- `3406` — свечи;
- `4414` — рамы;
- `6702` — искусственные цветы.

Для таких товаров на контрольную дату это отражается как **`experiment = yes`**, а не как `future = yes`.

Исправление хранится в:

`data-src/batch-v2-zz-hobby-homeware-experiment-corrections-01.json`.

Префикс `zz` используется намеренно: пакет загружается после более ранних `batch-v2-*` и может точечно перезаписать карточки с теми же ID.

## Архитектура репозитория

### `data-src/`

Исходные проверенные пакеты. Для нового массового наполнения это главный рабочий слой.

Современный универсальный формат:

`data-src/batch-v2-*.json`

Старые крупные категории могут иметь собственные исходные файлы и builders:

- одежда;
- обувь;
- детские товары;
- канцтовары;
- товары для животных;
- дом и сад;
- книги;
- мебель.

Не нужно мигрировать их в `batch-v2` без отдельной задачи.

### `scripts/build_batch_v2.py`

Универсальный сборщик новых пакетов.

Он:

- объединяет источники;
- разворачивает reusable `profiles`;
- строит варианты ТН ВЭД;
- вычисляет итоговый GREEN/YELLOW/RED;
- формирует summary;
- пишет подробные карточки;
- формирует сценарии;
- обновляет статистику.

Важная логика `derived_result`:

- все варианты GREEN → итог GREEN;
- все варианты RED → итог RED;
- смешанные варианты → итог YELLOW.

Поэтому итоговый цвет должен следовать вариантам, а не вручную придуманному верхнеуровневому `result`.

### `data/compliance-summary.json`

Краткий индекс проверенных карточек.

Пример:

```json
{
  "123": {
    "result": "yellow",
    "markingCurrent": "no",
    "markingFuture": "no",
    "experiment": "yes",
    "documentFlags": ["refusal"],
    "tnvedCodes": ["3926909709"],
    "lastChecked": "2026-08-27"
  }
}
```

Если ID отсутствует в итоговом summary, он считается `pending`.

### `data/compliance/details/XXXXX-XXXXX.json`

Подробные карточки по диапазонам 500 ID.

Содержат:

- нормализованное название;
- маркировку;
- варианты ТН ВЭД;
- характеристики для уточнения;
- документы;
- источники;
- причину screening-статуса;
- дату проверки.

### `data/rules/products/XXXXX-XXXXX.json`

Хранилище готовых сценариев классификации.

Интерфейс показывает все реалистичные сценарии сразу. Пользователь не должен выбирать фиктивные checkbox/radio только ради получения заранее неизвестного 10-значного кода.

### `data/sources.json`

Единый справочник источников.

### `data/regulations.json`

Центральная база нормативных правил, независимая от категорий Ozon.

Правило может содержать:

- тип требования;
- `active / future / experiment / expired / review`;
- даты действия;
- ТН ВЭД;
- ОКПД2;
- условия сопоставления;
- эффект для screening;
- источники;
- дату проверки.

### `data/regulatory-impact.json`

Генерируемая очередь потенциально затронутых товаров.

Это не автоматическое юридическое решение. Совпадение по ТН ВЭД лишь показывает, какие карточки нужно перепроверить при изменении законодательства.

### `data/catalog-gz/`

Сжатый полный каталог Ozon. Браузер загружает и склеивает его при открытии сайта.

### `assets/`

Frontend статического сайта.

### `.github/workflows/deploy-pages.yml`

Полный pipeline проверки, сборки и публикации.

## Формат нового `batch-v2`

Упрощённый пример:

```json
{
  "schemaVersion": 2,
  "batchId": "hobby-example-01",
  "checkedAt": "2026-08-27",
  "mainCategory": "Хобби и творчество",
  "sources": {
    "source-id": {
      "title": "Название официального источника",
      "authority": "Орган",
      "url": "https://..."
    }
  },
  "profiles": {
    "simple": {
      "marking": {
        "current": {"status": "no"},
        "future": {"status": "no"},
        "experiment": {"status": "no"}
      },
      "documents": {
        "status": "none",
        "items": [],
        "refusalLetter": "Вероятно возможно после подтверждения точного кода",
        "basis": "Основание вывода"
      },
      "sourceIds": ["source-id"]
    }
  },
  "products": [
    {
      "id": 1234,
      "name": "Название типа товара из каталога Ozon",
      "subcategory": "Подкатегория",
      "screeningReason": "Почему присвоен такой уровень сложности",
      "influences": ["материал", "назначение"],
      "variants": [
        {
          "code": "3926",
          "when": "Если изделие фактически из пластмассы",
          "result": "green",
          "confidence": "средний",
          "profile": "simple"
        }
      ]
    }
  ]
}
```

### Что обязательно должно быть продумано для каждого продукта

1. `id` — точный ID каталога.
2. `name` — не переименовывать произвольно, сохранять тип товара Ozon.
3. `subcategory` — категория из каталога.
4. `screeningReason` — короткое объяснение результата.
5. `influences` — только реально влияющие на ТН ВЭД / документы / маркировку характеристики.
6. `variants` — реалистичные сценарии, а не формальные дубли.
7. `code` — только подтверждаемая степень точности.
8. `when` — понятное условие выбора варианта.
9. `result` — GREEN/YELLOW/RED для конкретного варианта.
10. `confidence` — насколько надёжен предварительный ТН ВЭД.
11. `marking`, `documents`, `sourceIds` — напрямую или через `profile`.

## Как продолжать наполнение

Рабочий цикл для новой группы:

1. Найти следующие `pending` ID в выбранной основной категории.
2. Разбить их на нормативно однородные подгруппы, а не анализировать огромный смешанный список одним правилом.
3. Для каждой подгруппы определить, какие нормативные режимы реально возможны.
4. Проверить ЧЗ текущий / будущий / эксперимент отдельно.
5. Проверить технические регламенты ЕАЭС и иные специальные режимы.
6. Определить реалистичные ТН ВЭД, не завышая точность.
7. Сформировать `profiles`, чтобы не копировать одинаковые нормативные блоки десятки раз.
8. Сформировать `products` и `variants`.
9. Добавить новый `data-src/batch-v2-...json`.
10. Сделать push в `main`.
11. Проверить GitHub Actions.
12. Убедиться, что завершились успешно как минимум:
   - validation regulatory registry;
   - Python/JavaScript validation;
   - все builders;
   - `Build regulatory impact queue`;
   - `Upload artifact`;
   - `Deploy`.
13. Из job logs взять фактическую строку вида:

```text
Batch v2 merged ... products; total ...; stats {'green': ..., 'yellow': ..., 'red': ...}
```

14. Только после `Deploy = success` считать пакет опубликованным.

## Важная особенность GitHub Actions

Workflow имеет:

```yaml
concurrency:
  group: pages
  cancel-in-progress: true
```

Если сделать новый push, пока старый deploy ещё работает, старый run может быть отменён автоматически.

В такой ситуации не нужно чинить отменённый run, если новый commit содержит все предыдущие изменения. Нужно дождаться результата более нового run.

---

## Генерируемые файлы и `main`

GitHub Actions пересобирает данные внутри runner перед публикацией Pages.

Поэтому при определении **самой свежей опубликованной статистики** нельзя слепо считать, что закоммиченный `data/meta.json` или `data/compliance-summary.json` всегда равен последнему Pages artifact.

Надёжная контрольная последовательность:

1. последний commit `main`;
2. соответствующий Actions run;
3. `conclusion: success`;
4. строки статистики из job logs;
5. опубликованный Pages artifact / сайт.

Исходные `data-src/*.json` — долговременная база выполненной аналитической работы.

## Центральный нормативный слой и обновления законодательства

При появлении нового постановления или изменения маркировки сначала нужно проверить, можно ли оформить его как центральное правило в `data/regulations.json`.

Принцип:

`товар → возможные ТН ВЭД → нормативное правило → потенциально затронутые карточки → ручная проверка условий`.

Не нужно массово менять карточки только из-за совпадения группы ТН ВЭД.

Если область действия нормативного акта требует дополнительные признаки, они должны быть проверены отдельно.

`data/regulatory-updates.json` используется как журнал изменений и политики перепроверки.

## Контроль качества

Перед публикацией GitHub Actions автоматически выполняет:

1. `scripts/validate_regulatory_data.py`;
2. Python syntax-check builders;
3. `node --check` frontend JavaScript;
4. сборку старых специализированных категорий;
5. сборку всех `batch-v2-*.json`;
6. сборку мебели;
7. построение `regulatory-impact.json`;
8. создание Pages artifact;
9. deploy GitHub Pages.

Но автоматическая техническая проверка не доказывает правильность нормативной классификации. Качество ТН ВЭД, ЧЗ и документов обеспечивается источниками и ручным анализом каждого нормативно однородного блока.

## Что новому чату нельзя делать

- Не начинать базу заново.
- Не присваивать GREEN массово только по «простому» названию товара.
- Не считать эксперимент обязательной маркировкой.
- Не считать новость или проект НПА утверждённым `future`.
- Не выдумывать 10-значный ТН ВЭД при недостатке характеристик.
- Не переносить требования готовой продукции на сырьё без проверки области применения регламента.
- Не переносить требования взрослого товара на детский и наоборот.
- Не считать отсутствие ЧЗ отсутствием других обязательных требований.
- Не использовать отказное письмо вместо обязательного документа.
- Не считать пакет опубликованным до успешного Pages deploy.
- Не редактировать вручную сотни generated-файлов, если задачу решает новый `data-src/batch-v2-*.json`.
- Не удалять старые пакеты, если нет подтверждённой причины их заменить.

## Основная цель дальнейшей работы

Постепенно пройти все **9 308** сочетаний каталога Ozon и превратить `pending` в проверенные GREEN / YELLOW / RED карточки с проверяемыми источниками, реалистичными вариантами ТН ВЭД и понятной логикой документов.

Основной практический приоритет при отборе товаров — находить позиции с низкой регуляторной нагрузкой, без обязательного Честного знака и, где это реально допустимо после точной классификации, со сценарием отказного письма вместо обязательной сертификации/декларирования.
