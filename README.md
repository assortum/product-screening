# Product Screening

Статическая поисковая база для первичного товарного compliance-screening перед отбором ниш на Ozon.

## Текущее состояние

- импортировано 9 308 сочетаний `Основная категория → Категория → Тип товара`;
- 8 980 уникальных названий типов товаров;
- 30 основных категорий;
- регуляторные выводы не присваиваются автоматически только по названию товара;
- проект рассчитан на GitHub Pages и не требует backend.

## Логика статусов

Цвет показывает регуляторную сложность входа, а не решение `продавать / исключить`:

- `green` — **ПРОСТОЙ ВХОД**: низкая регуляторная нагрузка;
- `yellow` — **ВНИМАНИЕ**: есть развилка по классификации или нормативный риск;
- `red` — **СЛОЖНЫЙ ВХОД**: существенные обязательные требования;
- `pending` — **НЕ ПРОВЕРЕНО**.

## Что показывает карточка товара

Карточка не пытается вычислить окончательный ТН ВЭД через переключатели характеристик. Вместо этого она показывает все реалистичные сценарии, уже подготовленные для типа товара:

- возможный ТН ВЭД или группа/подгруппа;
- когда этот вариант применим;
- Честный знак сейчас;
- утвержденный будущий этап Честного знака;
- эксперимент / пилот отдельно от обязательной маркировки;
- декларация, сертификат, СГР и другие обязательные документы;
- вероятность/возможность отказного письма;
- нормативные источники;
- дата последней проверки;
- перечень характеристик, которые влияют на окончательный 10-значный код.

Если точный 10-значный код нельзя определить по уровню `категория Ozon + тип товара`, база показывает более широкую группу и прямо помечает, что код требует уточнения.

## Специализированный ассистент ТН ВЭД

В карточке есть отдельный блок **«Уточнить ТН ВЭД у ассистента»**.

URL хранится в `data/manifest.json`, а не зашит в интерфейс:

`https://chatgpt.com/g/g-69f2fdccdb3c8191ad9b7e2daf4c9f20-tn-ved-marketpleisy`

Кнопка **«Скопировать данные для проверки»** формирует готовый текст с товаром, категорией Ozon и предварительными вариантами ТН ВЭД. Пользователь добавляет фото, материал, состав, назначение и технические характеристики уже в специализированном ассистенте.

## Архитектура данных

### Каталог

Поисковый каталог хранится в сжатом виде в `data/catalog-gz/`. При открытии сайта браузер склеивает фрагменты, распаковывает gzip и получает все 9 308 записей.

### `data/compliance-summary.json`

Краткий индекс проверенных товаров. Используется поиском и фильтрами.

```json
{
  "123": {
    "result": "yellow",
    "markingCurrent": "no",
    "markingFuture": "no",
    "experiment": "yes",
    "documentFlags": ["refusal"],
    "tnvedCodes": ["3926909709"],
    "lastChecked": "2026-08-27"
  }
}
```

Товар, которого в индексе нет, считается `НЕ ПРОВЕРЕНО`.

### `data/compliance/details/XXXXX-XXXXX.json`

Подробные карточки загружаются лениво по диапазонам 500 ID.

Здесь хранятся:

- описание текущего regulatory screening;
- возможные ТН ВЭД;
- общая картина ЧЗ;
- документы;
- источники;
- дата проверки;
- причины присвоенного уровня сложности.

### `data/rules/products/XXXXX-XXXXX.json`

Исторически эти файлы были деревьями вопросов. Теперь интерфейс использует их как **хранилище готовых сценариев классификации**.

Пользователь не выбирает radio/checkbox. Все сценарии отображаются сразу и при необходимости группируются по одинаковым:

`ТН ВЭД + ЧЗ + документы + уровень риска`.

Это позволяет сохранить уже выполненную работу и постепенно повышать точность кодов без переделки интерфейса.

### `data/sources.json`

Единый справочник нормативных источников. Карточки и центральные нормативные правила ссылаются на `sourceId`.

Предпочтение отдается официальным источникам:

- `publication.pravo.gov.ru`;
- `government.ru`;
- `eec.eaeunion.org`;
- `markirovka.ru`;
- профильным государственным ведомствам.

## Центральный нормативный слой

### `data/regulations.json`

Это отдельная база законодательства, не привязанная жестко к категориям Ozon.

Нормативное правило содержит:

- тип требования;
- статус `active / future / experiment / expired / review`;
- дату начала/окончания;
- ТН ВЭД;
- ОКПД2, если требуется;
- логику сопоставления;
- эффект для screening;
- официальные источники;
- дату последней проверки.

Принцип:

`товар → возможные ТН ВЭД → центральные нормативные правила → затронутые карточки`.

Поэтому при появлении нового Честного знака не требуется вручную читать все 9 308 карточек заново.

### `data/regulatory-updates.json`

Журнал нормативных изменений и политика перепроверки.

Проект документа или эксперимент не считаются утвержденной будущей обязательной маркировкой без соответствующего нормативного акта.

### `data/regulatory-impact.json`

Файл генерируется автоматически при публикации сайта скриптом `scripts/build_regulatory_impact.py`.

Он определяет, какие уже проверенные товары потенциально пересекаются с каждым нормативным правилом по возможным ТН ВЭД.

Это **очередь на проверку**, а не автоматическое юридическое заключение. Если правило требует одновременно ТН ВЭД + ОКПД2 + наименование, совпадение только по ТН ВЭД считается потенциальным и не меняет карточку само по себе.

## Контроль качества при публикации

GitHub Actions перед каждым deploy выполняет:

1. проверку целостности `data/regulations.json`;
2. проверку существования всех `sourceId`;
3. проверку статусов и дат нормативных правил;
4. `node --check` всех JavaScript-файлов интерфейса;
5. сборку всех заполненных товарных пакетов;
6. построение `regulatory-impact.json`;
7. публикацию GitHub Pages только после успешного прохождения предыдущих шагов.

## GitHub Pages

`https://assortum.github.io/product-screening/`

После каждого push в `main` база пересобирается и публикуется автоматически.

## Локальный запуск

```bash
python -m http.server 8000
```

Затем открыть:

`http://localhost:8000/`

Через `file://` проект открывать не следует, так как браузер блокирует часть `fetch`-запросов к JSON.
